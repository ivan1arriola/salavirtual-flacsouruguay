### Caos concreto, por impacto

1. **Lecturas repartidas y trabajo común excesivo.** `obtenerDatosPaginaConfiguracion` carga credencial Workspace, asistencia, todas las cuentas, conteos y operaciones Meet para cualquier sección (`configuracion-page.service.ts:29-106`); después `page.tsx` agrega consultas propias de Zoom, SES y auditoría (`page.tsx:45-59`). La página también interpreta auditorías y construye modelos visibles (`page.tsx:61-75,207-250`). Hay dos sitios que deben mantenerse coordinados al cambiar una sección.

2. **Reglas de negocio dentro del transporte.** `/salas-meet/route.ts` contiene esquemas, reglas Meet/Zoom, transacciones, cifrado, auditoría y validaciones de borrado (`:16-50,63-122,128-315`); el componente también arma el payload según proveedor (`meet-hosts-config.tsx:207-303`). En cambio, Zoom y Workspace sí delegan buena parte a servicios (`zoom/route.ts:60-72`, `google-workspace/route.ts:78-108`). `api.ts:1-67` mezcla fachada de credenciales, correo, página, sincronización y dominios; su nombre no distingue API HTTP de API interna.

3. **Tres experiencias de guardado.** Salas/Zoom/Workspace manejan `fetch` y estado local (`meet-hosts-config.tsx:34-83`, `zoom-config-form.tsx:23-88`, `workspace-config.client.ts:100-115`); SES y Monitoreo usan acciones con redirect y mensajes por query string (`actions.ts:130-160`, `page.tsx:172-173,235`). La carga tampoco es uniforme: Workspace Legacy tiene `loading` propio (`workspace-legacy-credentials.tsx:16-29`), Drive y delegación solo cambian mensajes (`workspace-drive-form.tsx:8-32`, `workspace-delegation-form.tsx:10-22`), y Zoom distingue `saving` de `testing` (`zoom-config-form.tsx:23-25`). Esto explica por qué el conjunto se siente fragmentado aunque cada formulario funcione.

4. **Nombres y estilos dificultan encontrar el dueño de cada cosa.** `meet-hosts-config.tsx:21-30,207` administra también Zoom; `salas-meet/route.ts:16-19` acepta ambos proveedores. `program-members-config.tsx` vive en componentes generales y sus acciones en Configuración aunque la vista está en Usuarios. Zoom tiene varios `style={{…}}` (`zoom-config-form.tsx:140,186,201,218,227`); Workspace Credential usa un módulo CSS (`workspace-credential-form.tsx:27`) y el resto depende mayormente del CSS global importado por `app/(gestion)/layout.tsx:11`.

**Tamaños, contando líneas físicas:** `settings.css` **1296**, `workspace-credential-form.module.css` **556**, `workspace-credential-form.tsx` **459**, `google-workspace.service.ts` **459**, `salas-meet/route.ts` **443**, `meet-hosts-config.tsx` **304**, `program-members-config.tsx` **261**, `configuracion/page.tsx` **254**, `zoom-config-form.tsx` **244**, `configuracion/actions.ts` **232**, `configuracion-page.service.ts` **225**. ### Riesgos del refactor

- **Tests atados a rutas y nombres.** No encontré un test que lea `configuracion/page.tsx`, `meet-hosts-config.tsx` o `salas-meet/route.ts` como texto. Sí hay uno que lee literalmente el CSS compartido: `test/usuarios-responsive-table.test.ts:4-5,21-25` depende de `app/(gestion)/settings.css` y de selectores concretos. `test/cuentas-zoom-grupo-schema.test.ts:1-5` y `test/schema-contract.test.ts:1-4` leen el schema como texto. Otros importan rutas o módulos por ubicación: `test/salas-meet-route.test.ts:40`, `test/resincronizar-cohosts-route.test.ts:37`, `test/f9-sensitive-admin-reads.test.ts:46-60`, `test/settings-navigation-domain.test.ts:4-9`, `test/meet-hosts-config-domain.test.ts:2` y `test/program-members-config-domain.test.ts:2`. Mover archivos exige actualizar esos imports y conservar el comportamiento probado.
- **Contratos HTTP y consumidores fuera de la pantalla.** Conservar URL, métodos y forma de respuesta mientras se cambian interiores. Los clientes están en `workspace-config.client.ts:28-105`, `meet-hosts-config.tsx:291`, `zoom-config-form.tsx:33,66` y `email-test-form.tsx:17`. Además, los servicios de credenciales y correo alimentan reuniones, conferencias, notificaciones y migración histórica (`app/api/v1/reuniones/instancias/[instanciaId]/iniciar-zoom/route.ts:8`, `src/modules/conferencias/infrastructure/google/google-conference-provider.adapter.ts:30`, `src/modules/notificaciones/notificaciones.service.ts:2`, `src/bootstrap/migracion-zoom.server.ts:14-15`).
- **Datos reales y secretos.** El schema persiste claves Workspace cifradas, secreto OAuth Zoom, configuración SES y `CuentaProveedor.secretRef` (`prisma/schema.prisma:87-140,244-251`). La ruta Salas además audita cambios y restringe operaciones sobre cuentas usadas (`salas-meet/route.ts:69-122,128-315`). Un refactor de UI no debería cambiar esquema, cifrado, identificadores `principal` ni semántica de Principal/Legacy. La nueva lógica de grupo Zoom agrega otro dato persistido (`prisma/schema.prisma:103-119`).

### Estructura objetivo y orden

**Convención para la UI:** lecturas en funciones servidor por sección, que entreguen un modelo visible sin secretos; comandos iniciados por la UI mediante Server Actions que llamen servicios de aplicación. Los Route Handlers existentes quedan como adaptadores de compatibilidad sobre **los mismos servicios**, y los GET necesarios para paginación o diagnóstico siguen siendo HTTP. Así hay un solo lugar para autorización de negocio, validación, auditoría y persistencia, y un patrón consistente de estado pendiente/error en los formularios. Next 16 permite este uso de Server Actions, siempre con autorización dentro de cada acción (`07-mutating-data.md`, sección “What are Server Functions?”).

Carpetas sugeridas: `src/modules/configuracion/{domain,application,infrastructure,presentation}/` con subcarpetas `workspace`, `zoom`, `cuentas-proveedor`, `correo` y `monitoreo`; `app/(gestion)/configuracion/` conserva solo página y adaptadores de acciones; `app/api/v1/configuracion/**` conserva contratos HTTP. Mover Programas a su módulo dueño en una etapa aparte; no hacerlo pasar por una sección que ya redirige.

Orden de entregas separadas:

1. **Tras integrar la rama Zoom**, fijar contratos visibles y tests de cada flujo; registrar la forma de respuestas y las reglas de cuentas Meet/Zoom. Riesgo bajo; evita cambiar comportamiento por accidente.
2. Extraer lecturas y transformaciones de `page.tsx` a consultas por sección, manteniendo URLs y componentes. Riesgo bajo a medio: conteos/resumen y auditoría de correo.
3. Extraer reglas, transacciones y auditoría de `salas-meet/route.ts` a un servicio de cuentas por proveedor; dejar la ruta como adaptador con el mismo contrato. Riesgo alto: cuentas activas, contraseñas cifradas y eventos asociados.
4. Unificar estados y errores de formularios, empezando por SES/Monitoreo y luego Workspace/Zoom/Salas. Migrar cada comando de UI a una acción que reutilice el servicio; mantener las rutas HTTP durante la transición. Riesgo medio: redirects, refresco de datos y pruebas de integración.
5. Separar paneles y CSS por sección, retirar `style` inline y aislar reglas de `settings.css` sin romper Usuarios. Riesgo visual medio; `usuarios-responsive-table.test.ts` requiere atención.
6. Reubicar Programas y adelgazar `api.ts` solo cuando sus importadores estén identificados. Riesgo medio por uso desde `/usuarios` y otros módulos.

**Todavía no tocar:** `configuracion-page.service.ts`, `salas-meet/route.ts`, `meet-hosts-config.tsx` ni la sección Salas de `page.tsx` antes de integrar `feat/cuentas-zoom-por-grupo`. Esa rama modifica los cuatro; iniciar ahí la extracción de cuentas produciría conflictos y, peor, podría separar las reglas nuevas de sincronización de grupo. Primero integrar y verificar ese flujo; después tomar ese estado como base del paso 3.
